## 0. 这个包是什么，现状如何

**已经在作者机器上验证通过的**（原始面板页摘录：`07-证据/s151-关键页摘录.txt`）：

| 能力 | 判定行 | 出处（摘录页） |
|---|---|---|
| GPU 上电并退出安全模式 | `[gpu zap] st=0 step=30 sec=0 tr=1 ld=0` | slot 10 |
| Metal 客户端渲染 | `[metal gpu7] backboard s34 e0 v4/4 … a256/0`（`/0` = 零错误） | slot 285 |
| 帧呈现到面板 | `[metal gpu7] PF 1/0 r0 v1/0 t38 a38`（另有 `PF 6/0 r0 v4/0`） | slot 47 / 69 |
| 显示交接 | `[gop] arg=1 step=7` + `[fb] … match=1` | slot 0 |
| GPU 接走扫描输出 | `SWAP  calls=21 accepted=21 rejected=0 \| gpu offers=19 done=19 failed=0` | slot 186 |
| 触摸进内核并发布 | `TOUCH HID … drv=1 … touch-reports=116 res=0` + `TX c=2 1068,2505 …` | slot 443 / 441 |

> **`touch-reports` 是逐步涨上去的**：slot 0 是 `0`、`res=-1`（开机时没人碰），中途 `16`，
> 到 slot 443 是 `116`、`res=0`，并且 slot 441 有一帧真实坐标 `TX c=2 1068,2505 w=6634 n=8 hid=22096/1`。
> 所以「触摸发布」这一格是有**真实触摸事件**背书的，不只是 `drv=1`。你上手划一下，这个数必须涨。

**还没解决的**：桌面（SpringBoard）长时间运行稳定性。包里的 payload 是**验证过 GPU+触摸的那一版**
（stage179），不是最新开发版——最新开发版带 WiFi 实验 rung，会让机器在 7~17 分钟后自己复位，
**不要拿来测 GPU**。

## 3. 快速开始

### 3.1 先编 UEFI（如果 `02-UEFI/SILICIUM_UEFI.fd` 不是你要的那版）

```bash
git clone https://github.com/WQSQW/uefi-dby_w09.git
cd uefi-dby_w09
git checkout 423e222          # patch 的基线
git apply /path/to/uefi-dby_w09-改动.patch
python3 build_uefi.py -d dby_w09
# 产物（默认 RELEASE，脚本里 -r 的默认值就是 RELEASE）：
#   Build/dby_w09Pkg/RELEASE_CLANGPDB/FV/SILICIUM_UEFI.fd
#   ./Mu-dby_w09.img          ← 这个才是可刷的东西：BootShim.bin + FD + dby_w09.dtb，boot header v2
```

> `-r DEBUG` 才是调试构建，产物在 `Build/dby_w09Pkg/DEBUG_CLANGPDB/FV/`。第一版文档把这两个写反了。

细节与常见错误见 `02-UEFI/说明-如何重建UEFI.md`。

### 3.2 再编 payload（必须换成你自己机器的三处输入）

见 `03-payload/说明-payload与换机重打.md`。核心命令：

```bash
cd <UniXNU 检出>
export UNIXNU_UEFI=<uefi 检出>
./unixnu defconfig dby_w09_defconfig -D ../UniXNU-dby_w09 --uefi "$UNIXNU_UEFI"
./unixnu build kernel -j 16 -D ../UniXNU-dby_w09 --uefi "$UNIXNU_UEFI"
./unixnu build payload -D ../UniXNU-dby_w09 --uefi "$UNIXNU_UEFI" \
    --edk2 "$UNIXNU_UEFI/Mu_Basecore" \
    --unique-chip-id <你的值> \
    --trust-cache <你的 original-static-system.bundle> \
    --owner-trust-cache <包>/04-GPU插件/owner-trust.bundle \
    --gpu-addon        <包>/04-GPU插件/gpu-addon.bin \
    --data-ramdisk <你的 Data 种子> \
    --out /root/unixnu-out
```

> **要 1:1 复现随包镜像，构建前把 `05-源码/src/board-stage179.toml` 拷成 `board.toml`。**
> 随包镜像的 48 条参数就写在那份文件里，逐字节从镜像读出来的（§5）。
> 包里的 `board.toml` 是**更新**的配置（51 条、920 字节），带背光/音频/电池/手电筒，**不是**这个镜像的配置。

### 3.3 刷机

**两件东西，两个分区，别弄反：**

```powershell
fastboot flash boot    Mu-dby_w09.img     # UEFI 固件（BootShim + .fd 打成的 boot image）
fastboot flash preload payload.img        # 内核 payload，约 208 MiB
fastboot continue
```

| 东西 | 分区 | 说明 |
|---|---|---|
| `Mu-dby_w09.img`（= BootShim + `SILICIUM_UEFI.fd` + ramdisk + dtb） | **`boot`** | `.fd` **不能**单独刷。它是 FV 镜像，不是分区镜像 |
| `payload-stage179-touch-gpu.img` | **`preload`** | 放 `preload` 是因为 `cache` 只有 104 MiB，装不下 208 MiB 的 payload |
| — | **`userdata` 永远不要写** | 这块分区里是 iPadOS 根卷 |

> ⚠️ **把 `.fd` 直接写进任何分区都会变砖**：它没有分区头，写进去之后 ABL 读不出 boot image，
> 设备只剩 EDL。刷 `boot` 分区请用脚本打出来的 `Mu-dby_w09.img`。

> ⚠️ **刷 `boot` 之前先留退路。** 作者这台机器的 LUN0 GPT 里**没有叫 `boot` 的分区**
> （`07-证据/lun0-partitions.txt` 全部 40 行：… `super` / `version` / `preload` / `userdata`），
> 所以 `fastboot flash boot` 这个名字是 **bootloader 自己解析的别名**，不是 GPT 里的一段偏移。
> 后果：**本包不提供 boot 的 EDL 兜底**（没有 boot 的 first_lba，也没有写 boot 的配方）。
> 刷之前请自己确认两件事：
>
> 1. `fastboot getvar partition-size:boot` 有输出、且 ≥ 8.4 MB（说明这个别名在你机器上存在）；
> 2. 你手上有这台机器**原来的 boot 镜像**（华为原厂固件里的 `boot.img` / `ramdisk.img`），
>    写坏了用它刷回去——**前提是 fastboot 还能用**；包里没有这份备份。

### 3.4 设备进不了 fastboot 时：走 EDL 写 preload

```powershell
# 前提：已装 QSaharaServer / fh_loader，9008 驱动正常，设备在 EDL
.\06-工具\flash-preload-edl.ps1 -Image <包>\03-payload\payload-stage179-touch-gpu.img -Go
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `-Image` | 必填 | 要写的镜像 |
| `-Go` | 关 | **不加就只做 dry run**：不发任何写命令（设备仍须在 EDL，否则脚本直接报 `no QDLoader 9008 on COMxx`），并且会先往 `06-工具/edl/` 落一个 XML。要真写必须加 |
| `-Port` | `COM14` | 9008 串口名，**不要带 `\\.\` 前缀**（脚本自己拼）。换口写 `-Port COM5` |
| `-ToolsDir` | 空 | 高通工具箱目录。目录里要有 `fh_loader.exe` + `qsaharaserver.exe`，**并且**在它的父目录下要能找到 `Huawei865870_devprg.elf`（没有就 `throw`）。给了就先在它里面找，找不到再回落到作者的 `C:\Users\HW\Desktop` |
| `-SkipSahara` | 关 | 设备已经在 Firehose（programmer 已加载）时加，跳过 Sahara 阶段 |
| `-ExpectSha` | 空 | 填上镜像的 sha256，脚本写之前会核对，不匹配就拒绝 |

脚本按 `07-证据/lun0-partitions.txt` 里的实测几何写 LUN0 的 `preload`：**start_sector 2375168，
53248 个 4096 字节扇区**（= 218,103,808 B，正好等于镜像大小）。

> 这个脚本**只管 `preload`**。`boot` 分区没有 EDL 配方，原因见 §3.3 的警告。

> ⚠️ 这个偏移来自**作者这台机器**的 GPT（`07-证据/lun0-partitions.txt` 是原始 dump）。
> 同型号不同批次的机器分区表可能不同，**刷之前先用 `fh_loader --convertprogram2read` 读一遍
> 自己的 GPT**，确认 `preload` 的 first_lba 还是 2375168。写错偏移会覆盖相邻分区。

### 3.5 看结果

用 `06-工具/` 里的两个脚本从 EDL 读回日志，然后对照 §5 的行。

## 4. 换机必须改的三处（payload 是机器绑定的）

包里的 `payload-stage179-touch-gpu.img` 是**作者机器**的镜像：它带着作者的 Data 卷 UUID、作者设备的
chip id 和作者的 Data 种子。**直接刷到你机器上大概率起不来**（表现是卡菜单或早期 panic）。

| 输入 | 在哪 | 从哪来 |
|---|---|---|
| `root_match_volume_uuid` | `05-源码/src/board.toml` 的 **`[payload.adt]`** 表 | 你要启动的那套 iPadOS 的 Data/OS 卷 UUID |
| `--unique-chip-id` | 构建命令 | 你设备的芯片唯一 ID（十六进制） |
| `--data-ramdisk` | 构建命令 | 你自己设备的 Data 种子（Apple 原始材料，包里不带） |

`--gpu-addon` 和 `--owner-trust-cache` 用包里那两份即可——只与插件二进制有关，与机型无关。

## 5. 成功长什么样，以及这个镜像到底带了哪些参数

作者机器实测（`07-证据/s151-关键页摘录.txt` 是原始页）：

```
[gpu zap] st=0 step=30 sec=0 tr=1 ld=0
[gpu latch] irq=100000 last=100000 n=2 cpi=0 prot=0 fault=0 lcpi=0 lprot=0 st3=cccccccc pf=cccccccc
[gop] arg=1 step=7
[fb] scanout=9c000000 1600x2560 rb=6400 gop=9c000000 match=1
[metal gpu7] backboard s34 e0 v4/4 t27bd241c7 a256/0
[metal gpu7] PF 1/0 r0 v1/0 t38 a38
SWAP  calls=21 accepted=21 rejected=0 | gpu offers=19 done=19 failed=0 abandoned=0 fallback=0 last=0
TX c=2 1068,2505 w=6634 n=8 hid=22096/1
TOUCH HID started=1 drv=1 key-reports=0 touch-reports=116 res=0 | pad dots=0
```

判读要点：

- `[metal gpu7] … a256/0`：`a` 后面的 `/0` 是错误计数，**必须是 0**；
- `[fb] … match=1`：呈现目标和面板扫描缓冲是同一块内存，**必须 1**；
- `[gpu latch] … fault=0`：没有 UCHE/总线故障；
- `SWAP … rejected=0` 且 `gpu offers=N done=N failed=0`：GPU 真的把帧接过去了（不是 CPU 拷贝兜底）；
- `touch-reports` 要**在涨**（手指划一下）。刚开机没人碰时它是 `0`、`res=-1`，划几下就会变成正数、`res=0`。

### 5.2 `unit-scale` 为什么是 1（第一版文档在这里自相矛盾）

`offline-legacy-unit-scale` 决定 SpringBoard 拿到的逻辑分辨率：

| 值 | 逻辑分辨率 | 观感 |
|---|---|---|
| 1 | 1600 × 2560 pt | UI 只有一半大小（`[fb] … 1600x2560` 就是这一档） |
| 2 | 800 × 1280 pt | 接近 iPad Pro 11 的正常大小 |

**随包镜像里是 1**（`[fb] scanout=… 1600x2560` 与它一致）。作者在 11-08 把树里的值改回了 2，
但那个改动**没有进这个镜像**。包里的 `board.toml`（51 条）用的是 2，`board-stage179.toml`（48 条）用的是 1。

要用 2 就把 `board.toml` 当配置重打 payload；要复现这个镜像就用 `board-stage179.toml`。

## 6. 故障排查

### 6.1 卡在 UniXNU 菜单（最常见的报障）

**五秒钟现场判断：用手指点一下屏幕。**

| 现象 | 结论 | 下一步 |
|---|---|---|
| 菜单**有反应**（高亮/选中） | 屏幕仍由 UEFI 占用，内核不在前台 | 不是 GPU 问题：查启动菜单/固件配置，确认 `boot` 分区刷的是打过 patch 的 `Mu-dby_w09.img` |
| 菜单**没反应**，日志里 `touch-reports=` 在涨 | 触摸进了内核，只是没被显示 | **显示交接失败**，看下表 |
| 菜单**没反应**，`touch-reports=` 也不动 | 触摸根本没起来 | 查 `dby-touch=8` / `dby-touch-se=1` / `TOUCH HID … drv=` 是否为 1 |

| 日志现象 | 结论 | 修法 |
|---|---|---|
| `[gop] arg=0` | `sheng-fb-gpu=1` 丢了 | 加回该参数 |
| 没有 `[gop]` 行 | 显示交接阶段没执行到 | 查 §5.1 那 10 条显示参数（在 `board.toml` 的 `[payload] kernel_args` 里） |
| `[fb] match=0` | 呈现目标 ≠ 面板扫描缓冲 | 按该机显示基址调整 |
| 没有 `[fb]` 行 | legacy display 探针没绑上 | 该机显示节点/时序与作者机器不同 |
| `[metal gpu7]` 行里 `c`/`r`/`i` 非 0 | GPU 自检失败 | 这才是 GPU 问题，与显示无关 |

**最常见的误操作**：重打 payload 时只改了自己的卷 UUID，**把显示参数丢了**。

## 8. 校验整包

```bash
python3 01-校验/verify-package.py GPU交接-2026-11-12
```

它会：

1. 核对 `MANIFEST.json` 里每个文件的**字节数和 sha256**，并检查磁盘上有没有清单外的文件
   （`__pycache__`、`.pyc`、以及 EDL 脚本自己写出的两个 XML 不算——它们是用过工具之后才出现的）；
2. 检查关键文件（UEFI、payload、触摸五件套、`GeniSpi.c`、`board-stage179.toml`）是否齐全；
3. 解析 `board.toml` 的 `[kernel] archives`，**每个非 `component:` 配方要么在包里、要么在 §7 那 7 个核树脚本里**；
4. 解析 `patch_series`，**每条 `device:patches/…` 必须在包里**，并且**每个 series 文件里列出的 patch 也必须都在**
   （少一个 patch 就是半套补丁，构建会 apply 到一半）；
5. 扫所有 `.md`，**里面引用的每个 `0x-…` 包内路径都必须存在**；
6. 用 `06-工具/read-payload-args.py` 读镜像的命令行，**逐条比对 `board-stage179.toml`**；
7. 校验 `board.toml` 自己的命令行**不超过 1000 字节**（只验 stage179 与镜像是不够的）；
8. 校验 `SILICIUM_UEFI.fd` 的 FV 头（`_FVH` 魔数与 `FvLength`）。

任何一项不符都会非零退出并打印原因。

清单本身也要有个锚点——`--write` 会重新生成 `MANIFEST.json`，所以清单不能自己证明自己。
`01-校验/MANIFEST.sha256` 就是它上面那一层：里面只有一行 `MANIFEST.json` 的 sha256，
而 `MANIFEST.json` 故意不收录这个文件。校验脚本会把两者对上：

```
01-校验/MANIFEST.sha256  →  MANIFEST.json  →  包里其余每个文件
```

交付时这个值也写在发送消息里，收到包先对一眼（`Get-FileHash` 或 `sha256sum`）。

> 这里**不写死**那个数字：本文档自己也在清单里，写进去就变成自指，每次改文档都得改数字。
> 权威值只有两处——`01-校验/MANIFEST.sha256` 和交付消息；校验脚本每次运行也会把它打印出来。

## 10. 已知缺口（不隐瞒）

1. **payload 是作者机器绑定的**：必须按 §4 重打。
2. **`02-UEFI/SILICIUM_UEFI.fd` 的构建类型**：`build_uefi.py` 默认出 RELEASE，但包里这个 `.fd`
   是作者早先构建的，**包里没有任何东西能证明它当时用的是哪个模式**（FV 内容压缩过，
   `grep GpuAddon` 也搜不到，见 `02-UEFI/说明-如何重建UEFI.md`）。唯一可靠的确认方式是开一次机看
   `DARWINBOOT: addon 0x… … bytes` 那行。要确定版就按 §3.1 自己重编。
3. **UEFI 的 163 行改动还没提交到上游**：patch 是相对 `423e222` 的，验证过可干净应用；
   如果你从上游 clone，**必须打这个 patch**，否则 GPU addon 不会被交接
   （`kernel.macho.gpuaddon` 不会读、ADT 里没有 `GpuAddon` 属性）。
4. **桌面稳定性**：GPU 能渲染、能呈现，但 SpringBoard 长时间运行的稳定性没有解决（作者机器上仍偶发）。
5. **触摸固件**：v3 驱动从分区读固件（`native_ufs_abs_read`），分区布局不同的机器要确认路径。
6. **s151 那次开机前半段 `touch-reports=0`**：刚开机没人碰屏幕，`res=-1` 是正常的；划了之后涨到
   `116`、`res=0`，并出现真实坐标行。所以「触摸发布」的证据是有触摸事件的，不是只看 `drv=1`。
