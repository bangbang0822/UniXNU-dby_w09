## 1. 范围

交付：**dby_w09 的前台动画稳定呈现 120 帧**——面板运行在 120 Hz、连续 60 s 内
`sum p95 ≤ 8333 µs`（§8）、漏帧 < 0.5 %、无 > 33 ms 长帧、无 CP 重启。

**范围包含**（正面声明，避免"沉默被读成意图"）：

1. 本仓 `package/`、`drivers/GopFramebuffer/`、`drivers/Adreno740/`、`scripts/`、`board.toml` 的改动；
2. **独立固件仓 `uefi-dby_w09`** 里显示初始化的一处改动（S4）。该仓有自己的评审与提交约定，
   不在本仓 `AGENTS.md` 管辖内；本规格只规定它**必须产出**什么：一份可回退的 60 Hz boot image 与 sha256；
3. S5a 会在 `board.toml [payload] kernel_args` 这张**与 `wireless` 共享**的表上腾位——
   这是本规格唯一触碰共享预算的地方，程序见 §3.4。

**非目标**：

- 3D / 游戏负载的 120 帧（只覆盖 UI 合成与呈现）；
- HDR / 10-bit / 广色域（直扫要求 8-bit BGRA，放宽即破坏前提，见 N15）；
- macOS profile、iPadOS 27 profile；
- `wireless`、`input`、PCIe 的**代码与参数**改动（S5a 的腾位除外，且腾位不得删除它们的参数）；
- CPU 拷贝路径优化（天生 9.4–10.2 fps，只作兜底）；
- GPU 硬件抢占（A6xx 无此能力，`NativeAdrenoIrq.h:52`）；
- SPI 300 迁移到 GIC group 1（S1b，见 §12-I7）。

## 3. 约束与门

### 3.1 一次一个变量
每步一次 flash。§6 的每一步只允许一个可观测变量改变；**仪表与机制必须分两次**（S3a/S3b 即此拆分）。

### 3.2 评审
- 评审者为不参与实现的一方；结论写在 `.research/gpu-120/reviews/<step>.md`，
  格式为 `[BLOCKER|MAJOR|MINOR]` + `file:line`，commit body 引用该路径；
- **FAIL 同时拦住**构建、flash、`porting.toml` 的 `status` 推进与合并；
- **PASS 不代替 owner 批准**：每一次 flash（含 S0a）都要 owner 在记录里点名批准，
  批准写进当轮 `[[area.evidence]]` 的 `command` 或 `result`（`AGENTS.md:114-115`）；
- S4 另需固件仓自己的评审 + owner 批准。

### 3.3 回退物必须有生产者
**每次 flash 之前**（含 S0a）执行，缺一不可：

1. `sha256sum` 当前 payload → `cp` 到 `/root/payloads/<sha8>.img`；
2. 涉及 boot 的步骤（S4）：把**改动前**的 boot image 归档到 `/root/boot/<sha8>.img`；
3. 两个 sha256 写进本轮 `[[area.evidence]].result`；
4. 只有以上完成，才允许 `fastboot`。

没有这一步的"回退 = 上一份 payload"是空话，v1 因此被判 BLOCKER。

### 3.4 参数预算：只认门的输出
`board.toml [payload] kernel_args` 的权威数字**只有** `scripts/check-regression.py` 的
`kernel_args_bytes=` 一行（`ARG_LIMIT_BYTES = 1000`，`check-regression.py:60`、`:229-230`，
算法是 `" ".join(args)` 的字节长）。本规格**不复制**该数字，只规定程序：

1. 任何加点前先跑门并引用 `kernel_args_bytes=`；
2. 两条线（本规格与 `wireless`）**不得同时在飞**同一个加参数的改动；先落者成功后，后者重测并自行腾位；
3. 腾位时被删参数必须**先证明无读者**（全树 grep，读者 `file:line` 写进 `board.toml` 注释），
   删除清单与证据写进 `[[area.evidence]]`；
4. 参考值（仅供判断规模，不作为依据）：2026-11-24 实测工作树 **56 参数 / 995 字节**
   （含未提交的 `dby-pcie=10`）、HEAD **55 / 983**；`sheng-vsync=120` 含分隔空格共 **16 字节**。
   即：HEAD 有余量、工作树没有，**必须先腾位**。

### 3.5 不碰其他工作线的代码
`package/DbyPcie.cpp`、`docs/wireless-*`、`package/DbyTouch/*` 不在本规格代码改动范围；
`drivers/ShengUfs/*` 亦不在（S4 改的是独立仓 `uefi-dby_w09`，不是 `drivers/ShengUfs`）。

### 3.6 没有观测量就不上机
每一步必须在 §7 有"必须出现的行"；写不出这一行的步骤不许 flash。

### 3.7 不读未上电的寄存器
本 SoC 上未应答的设备读是 SError。任何新增寄存器读必须落在**本树已读过的同一批偏移**上；
本规格**不新增 MDP 映射**（2026-11-15 新建映射 `0xae01000` 在首帧后 abort）。

### 3.8 测量推翻规格时必须改规格
任何测量与本规格矛盾，先改本规格（v3）再继续，改动记在当轮 `[[area.evidence]].result`；
不得静默沿用旧假设。

## 5. 行语法（新增观测）

一行一个事实，`kprintf` 前缀，字段名固定，脚本按名取值，**限流 ≤ 1 行/秒**。

```
[frame] win=1000ms n=59 fps=59 p50=16667us p95=16800us max=17300us T=8333us panel=16804us budget120=0% b17=98% b25=2% b34=0% bo=0% late=0% miss=0% | vis=120 direct=118 copy=0 gpu=0 blank=2 backint=0 nostamp=0
[frame budget] n=59 of=120 p50=51000us p95=53000us max=53000us avg=51500us | nostamp=0 backwards=0
[frame loss] acc=120 shown=120 flips=118 not_shown=0 (0.0%) late=0 miss=0 blank=2
[gpu submit] n=1752 p0=12us p1=180us p2=9us p3=140us p4=260us p5=41200us | drain=39800us/1398 max=874685us waits=1398 timeouts=326 | hold=41200us/1748 max=43000us | wait=800us/1398 max=38000us free=340
[gpu ttbr] mode=1 ttbr_writes=1735 cpchk=0 cpimg=0/0
```

**阈值定义（v2 统一，消除 v1 的三处不一致）**，以 120 Hz 的周期 `T = 8333.33 µs` 为基准：

- `late` = 间隔落在 `(T, 1.5T]`，即晚了但没跳过刷新；
- `miss` = 间隔 `> 1.5T`（=12 500 µs），即**至少跳过一次刷新**——这才是"漏帧"；
- `not_shown` = `accepted − flips`，即"被接受但没上屏"，与间隔无关；
- `budget120` = 间隔 ≤ `T` 的比例。

S0b 的 `budget120` 与 `late` 在 60 Hz 面板上必然为 0 %/0，这是**预期**，不是故障。
`[frame]` 只在**连续动画**的窗口内有意义（静止桌面时相邻 flip 的间隔是"用户何时改动画面"，
不是帧率）；因此该行必须同时打印 `n`，且判定只在 `n ≥ 50 / s` 的窗口上进行。

**`[frame]` 的时间戳位置（第二轮复核 A2 修正）**——必须是"像素真的可见"的那一刻，五处：

| 路径 | 时间戳位置 | 说明 |
| --- | --- | --- |
| 直扫 | `latchTick()` 的 `finishTransfer(request,true)`（`:269`） | **不是** `:534` 的 `flip()`：那时只是写了寄存器，panel 还没取走 |
| 空白帧 | `:482` 的 `finishTransfer(request)` 之后 | 填完即可见 |
| CPU copy | `:626` 之后 | 拷完即可见 |
| GPU 提前退休（默认 `sheng-early-retire=1`） | `finishGpuSwap` 的 `gpuRetired` 成功分支（`:633-639`） | 这条路径**不经过** `:643`，v2 初稿漏了它 |
| GPU 非提前退休 | `:643` 之后 | — |

**`[gpu submit]` 的字段边界（第二轮复核修正）**：

- `p5` = `useVm` + `ring_->submitFramed`（`NativeAdrenoSubmit.cpp:538-567`），**排空在 `p5` 里面**；
- `drain` = 其中真正执行 `waitAll` 的时间，`drains` = 发生排空的**次数**（两者都必需，否则均值无分母）；
- **没有 `fence=` 字段**：method 5 内部不含独立的 fence 等待段；`[fence wait]` 的总量来自
  method 6 与显示路径，**与 method 5 不可相加**（第二轮复核 C5/D5 纠正了 v2 初稿的重复计数）；
- `lock=` 是 **`dispatch` 之前的锁争用等待**，不属于 method 5，也不属于 `p0..p5`。

| --- | --- | --- | --- |
| `[frame]` | `NativeLegacyDisplay.cpp` 的**四条路径共用的** `noteFrameVisible(kind)` + `BootLog.c` | 新数组 `native_legacy_visible[]`（**不叫** `native_legacy_frame[]`，该名前缀已被探针占用） | v1 放在 `latchTick()` 只统计直扫（`latchRequest` 仅在 `:536` 赋值）。v2 要求四条路径（直扫 `:534`、copy `:626`、GPU `:643`、空白 `:482`）都调用同一处 |

## 6. 阶段设计

每个阶段固定九行：**改动 / 行为变化 / 共享状态（还有谁用） / 不上机的检查 / 依赖 / 验收 /

### S0a — 观测三行（纯仪表）

### S2 — 去除"每次提交排空"（**本规格的关键**）

**为什么它是关键**（v1 把它当可选，评审判 BLOCKER）：`dispatch()` 在 `g.lock` 内
（`NativeAdrenoPublish.cpp:712-725`），而 mode 1 的 `useVm` 在锁内 `waitAll(2 s)`
（`NativeAdrenoSubmit.cpp:227-230`）。锁被持有整个排空期 ⇒ 全部 7 个客户端串行 ⇒
系统上限 ≈ 1/42.26 ms ≈ **23.7 次提交/s**。这就是"UI 卡"的根，也是 S1 只能改善其中 7.2 ms 的原因。

三条候选，**按 S0a 的 `drain` 数据择一**，一次只做一条：

| 选项 | 做法 | 代价 | 风险 |
| --- | --- | --- | --- |
| **S2-A**（首选） | 打开 CP 的 SMMU aperture（`qcom_scm_set_gpu_smmu_aperture`）→ `tableMode()` 自然为 2 → CP 在 ring 内换表，无需排空 | 依赖 §12-I2（ABI 未知，**全项目无实现**） | 高（CP 换表错会 fault；但驱动自带 `checkCpSwitch()` + 自动回退 mode 1，`Publish.cpp:1156-1178`） |
| **S2-B** | 把**排空移出全局锁**：dispatch 释放 `g.lock` → 等待 ring 静默 → 重新取锁 → 复核 ring 仍静默 → 写 TTBR0 → 提交 | 需要"切换在飞"状态机；竞态窗口需证明 | 中高（新竞态）。**注意：它缩短的是锁持有时间，不缩短 `waitAll` 本身**，因此验收看 `lock=`/锁持有而不是 `drain` |
| **S2-C** | 延续 v1 思路的上限削减：**禁止**。把 2 s 上限改成 20 ms 会把 42 ms 的成功排空变成"快速失败 + 丢帧"，且 §7 的判据会**空洞通过** | — | 已否 |

若三条都不可行，本规格的目标必须下调为"稳定 60"，并把它写进 `limits`——**不得**继续按 120 实施。

## 8. 完成定义（DoD）

1. `[frame budget] sum p95 ≤ 8333 µs`，且 `[frame] p95 ≤ 8340 µs`（= T 上取整，<1 % 余量）；
2. 连续 60 s：`[frame loss]` 的 `not_shown < 0.5 %`、`miss < 0.5 %`、`late` 可非零但不得连续出现 3 次、
   无 > 33 ms 长帧；`[gpu recovery]` 的 hangs 不增、`vmfail` 不出现；
3. `scripts/check-frame-timing.py --require-120` 返回 true；
4. N10 的 latch 上界证据在记录里（≤1.02×8333 µs）；
5. 触摸回归（拖动 n=1、inv=0、静止无幻触）与无线行不退化（N16）；
6. 60 Hz 与 120 Hz 两份 boot image 都可启动（N11），两份 sha256 都在记录里；
7. §8 每一条各成一条 `[[area.evidence]]`（kind、`command`、40 位 `revision`、`result` 含观测行原文）；
   三份哈希（payload、kernel、boot image）写进 `result`；
8. `porting.toml` 的 `display`/`gpu`/`diagnostics`/`firmware` 四区按 §6 的"记录"行更新，
   所有 `[预测]` 改成 `[实测]`，未达成项写进 `limits`；
9. 达标前 `status` 不得为 `device-verified`；`--write-baseline` 在以上全绿前禁止使用。

## 附录 B：预算算术（供评审复核）

- 提交串行上限：`1 / 42.26 ms = 23.7 /s` ⇒ 平均每帧预算若为 8.333 ms，需要 ≥ 120 次提交/s，
  当前差 **5 倍**；
- 当前每帧耗时（粗算）：`dispatch 42.26 ms + latch 8.51 ms ≈ 50.8 ms` ⇒ ≈ 19.7 fps 上限；**这是 `[推算]`**，
  S0b 的 `[frame budget]` 就是来把它变成 `[实测]`；**注意这不等于"当前实测 19.7 fps"**——
  实测的 118 flips 是"UI 有变化才翻页"，二者不是同一个量（第二轮复核矛盾 4 已指出）；
- **`[fence wait]` 的两行不能与 method 5 相加或相减**：`calls/timeouts` 来自 `native_adreno_fence_wait`
  （`NativeAdrenoSubmit::wait`，**排空与显示共用**），`outer waits/us` 来自 `native_adreno_wait_outer`
  （`Publish.cpp:656-686`）。v1/v2 初稿把"7.19 ms 的 fence 段"当成 method 5 的组成，**未经验证**；
  S0a 因此必须给 `Submit::wait` 加**调用者标签**（drain / display / client），否则这三类时间永远分不开；
- 两个分母都成立，引用时必须写清楚：`22 659 129 / 3150 calls = 7193 µs`（按 calls）、
  `22 659 129 / 3103 outer waits = 7302 µs`（按 outer waits）；即 `6 798 743 / 4 246 µs` 之类的合成数
  **一律视为错误**；
- S1 的收益上限要看 S0a 的调用者标签才知道（若排空占 `wait` 的大头，S1 同时改善排空；
  若 `wait` 主要来自显示路径，S1 只改善显示）。v2 不再给"~14 %"这种未经验证的数。
