# dby_w09 GPU 满 120 帧：上游全景、差距诊断与实施方案

- 日期：2026-11-24
- 对象：dby_w09（华为 MatePad 11，SM8250 / kona，Adreno 650，iPadOS 17.7.11 21H461）
- 上游对照：sheng（SM8550 / Adreno 740，官方参考板）与其余骁龙设备
- 取证材料：`.research/gpu-120/{a-sheng,b-highrefresh,c-our-blockers}.md`、
  `.research/gpu-survey/*`、`research/dby/DBY-W09-display-research.md`、本仓库 `porting.toml`
- 本文是方案，不含已合入的代码改动；所有改动都还没写、没评审、没上机。

## 0. 结论（先看这五条）

1. **硬件上 120 帧是可行的，不是"Adreno 650 不配"。** 面板三档刷新率（120/60/30）共用同一个
   pixel clock 584849 kHz，只差 `vtotal`（2827 / 5654 / 11308），**不需要动 PLL**
   （`research/dby/DBY-W09-display-research.md:74-83`、`:419`）。我按这组数反算过：
   584849 kHz ÷ htotal 1724 = 339.2 kHz 行频；÷ 2827 = **120.0 Hz**，÷ 5654 = **60.0 Hz**，
   ÷ 11308 = **30.0 Hz**，三档自洽。
   带宽也不拦路：1600×2560×4 B = 16.38 MB/帧，120 Hz 扫描读出 1.97 GB/s，GPU 再写一份 1.97 GB/s，
   合计约 4 GB/s，而 kona 的 LPDDR5 理论约 44 GB/s —— 占不到 10%。

2. **记录里"120 不是 A650 的数"这条结论，前提是错的。** `porting.toml:521` 用
   "GOP 拷贝 153 MiB/s ⇒ 10 fps 上限" 去否 120，但那是 **CPU 拷贝路径**的速率，
   不是 SoC 或 GPU 的上限；同一段还漏了"面板当前根本没跑 120Hz"这个更硬的限制。
   真实限制是**延迟**与**面板模式**，两者都不是算力。

3. **当前实测足以解释为什么现在上不去。** 性能轮（`.research/console-gpuperf2-2026-11-20.log`）：
   - `[gpu methods] 5:1752/0/74039183` → **Submit 平均 42.26 ms/次**；
   - `[fence wait] calls=3150 us=22659129 / ... polls=14150` → **每次等待 7.19 ms，每次 poll 1.60 ms**
     （我们要求的是 100 µs，超了 16 倍）；
   - `[direct scanout] longest=16804 total=1004162 flips=118` → latch 均值 8.51 ms、最大 16.80 ms
     = 1.008 × 16.667 ms，**面板实际在 60 Hz**。

4. **上游没有一家真正演示过"稳定 120 帧"。** sheng 请求 `vsync=120 vsync-fixed=1`，
   实测 `fps average 72.1 / 68.2`（低帧 41.5 / 35.2，**未写明用什么工具测**）；
   asteroids（A810，120Hz 面板）自评 **"Under 60 frames per second"**；pandora（A840）只有
   维护者目测"约 110 帧"；diting/thor/rmx3551 明写"120Hz 是请求值，不代表测得帧率"。
   所以"满 120 帧稳定"在这个项目里**没有可抄的成品**，只有可抄的**方法**。

5. **因此方案分两段：先把每帧预算从 42 ms 压到 1 ms 量级（这一段在 60Hz 下就能验收），
   再把面板切到 120Hz（一段独立的显示工程）。** 顺序不能反：面板先到 120、延迟不改，
   只会得到"120Hz 面板上的 24 帧"。

### 目标定义（可验收，不靠感觉）

> **满 120 帧稳定** = 连续 60 s、前台动画期间：
> 相邻 flip 间隔 **p50 ≤ 8.4 ms、p95 ≤ 8.4 ms**（120Hz 一帧 = 8.333 ms，留 1% 余量）、
> **missed-vblank < 0.5%**、**无一次 > 33 ms 的长帧**、**无 CP 重启、无 VM 毒化**。
> 达不到时退而验收 **稳定 60**：p95 ≤ 16.8 ms，missed < 0.5%。

## 1. 上游全景：谁在怎么做

### 1.1 sheng（SM8550 / A740，参考板）

**它的帧路径**（`.research/gpu-120/a-sheng.md`，逐条带 `path:line`）：

1. Metal → AdrenoMetal → metal2vulkan → Turnip；默认 `TU_DEBUG=gmem,nocb`（能平铺的 pass 在
   tile 内存里做完，一次 load/store）。
2. 提交走 ring 0（高优先级）/ ring 1（普通），显示侧读 `native_adreno_fences(submitted,retired)`。
3. 合成器**在 command buffer 被调度时就 swap，不是 GPU 写完才 swap**，所以显示侧在 flip 前
   先轮询 GPU fence（`gpuWrote()`，200 µs 定时器重试，最多等到 250 ms 记一次 `[12]`），
   **等 ≥8 ms 记一次 `[13]`（错过一个 120Hz 刷新）**。
4. 直扫：`directSlot()` 把 surface 的物理页映射进显示 bank 的 stage-1 窗口，flip 只写
   VIG0/1 的地址 + 16 位 stride + `CTL_FLUSH`。
5. latch 用 500 µs 轮询 flush 位，50 ms 上限，然后 swap 退休。
6. 兜底：GPU 客户端拷贝（`fb-gpu=1`，early retire）→ 再兜底 CPU 拷贝（**sheng 自己的实测
   143–285 ms/swap**）。

**它的关键参数**（`.research/upstream/sheng-board.toml`，iPadOS 27 那一组）：

```
gpu-power=9 gpu-metal=1 fb-gpu=1 fb-bgra=1 dpu-scanout=2
vsync=120 vsync-fixed=1 gpu-dcvs=1 gpu-addon=1 no-lc=1
```

**它的实测与自评**：

- `fps average 72.1 and 68.2`，低帧 41.5 / 35.2（两次引导各一组；**没有说明工具**）。
- 真正的分布数据是 flip 间隔：median `15.358 → 9.631 ms`，**P99 `43.232 → 46.384 ms`**。
- 仓库自带 `scripts/analyze-sheng-frame-timing.py`，输出 min/median/p95/max 与
  `over_120hz_budget(8333us)`，并把 `qualifies_stable_120fps` **硬编码为 False**，
  注释是"A copied framebuffer is not evidence of panel vblank or presentation"。
- vsync 是**工作环定时器**，不是面板 vblank：`"The GOP scanout has no vblank interrupt, so a
  work-loop timer stands in for it"`。
- 记录里**没有一句**解释"为什么是 ~70 而不是 120"；帧节拍被列为下一步待办。

**结论性判断**：sheng 给的是**架构与仪表**，不是达标的数字。它的 P99 46 ms 说明它自己也常在掉帧。

## 2. 我们 GPU 路线的不足（逐条带证据）

记号：**硬** = 不改就上不去；**软** = 可调；**仪表** = 不改就看不见。

### D1 面板从来没被设过模式，实际在 60Hz —— **硬**

- XNU 只**读**固件的 GOP 模式：`PE_current_console()` → `PE_Video` → 尺寸/stride/depth 一律沿用
  （`NativeLegacyDisplay.cpp:759-777`）；`dts/dby_w09.dts` 整整 2572 字节里**没有任何 panel/DSI 节点**。
- 也没有任何东西写 DSI 时序：DSI kick 那轮自己记着 "Nothing else is touched — VID_CFG0, the
  timings and the lane setup stay as the loader wrote them"（`porting.toml:347`）。
- 间接测量（可信）：直扫 latch 均值 8510 µs ≈ 16.667/2，最大 16804 µs = 1.008 × 16.667 ms；
  若面板在 120Hz，latch 最大只能到 8.33 ms。
- 面板本身支持三档，只改 VFP（`vtotal` 2827 / 5654 / 11308），但**切档要 full modeset + 面板
  off/on**（104 条开屏 + 5 条关屏命令），不是无缝 DFPS（`DBY-W09-display-research.md:82-83`、`:99-100`）。

**含义**：这是 120 的**唯一硬门**。在它被解决前，任何 GPU 优化最多把"60Hz 上的掉帧"变成"60Hz 上不掉帧"。

### D2 每次 Submit 42 ms —— **硬**（当前最大的单点）

- `[gpu methods] 5:1752/0/74039183`：1752 次调用、0 失败、合计 74.04 s → **42.26 ms/次**。
- 这不是 GPU 慢：`[gpu ibs] submissions=1753` 与 `gpu wrote=1753` 对齐，**交给 GPU 的活全做完了**。
- 时间花在"等"上，而且等得比设计值贵 16 倍（见 D3），再被"换页表前排空 ring"放大：
  `NativeAdrenoSubmit::useVm`（`NativeAdrenoSubmit.cpp:219-235`）在 mode 1 下
  `waitAll(clock, 2000000)` —— **等整个 ring 静默，上限 2 s**。
- 我们的表切模式**恒为 1**：`tableMode()` 读 `native_adreno_cp_aperture[0]`
  （`NativeAdrenoPublish.cpp:176-181`），而该数组在本仓库里**只有声明（零初始化）和 [2]/[3]
  两处写入**，`[0]/[1]` 从来没有写者 → 永远走 mode 1。
- sheng 用 mode 2（`gpu-preempt=2`，见 `porting_gpu.md:102`："The reference enables mode 2 …
  the CP switches in the ring"），换表不需要排空。

### D3 每次 fence poll 花 1.60 ms，而设计要求 100 µs —— **硬**

- `[fence wait] calls=3150 us=22659129`、`unlocked polls=14150` → 4.49 poll/次等待，
  7.19 ms/次 ⇒ **1.60 ms/poll**。
- 机制：板级没有提供 `clock.idle`（`DbyGpuPowerProbe.cpp:4485/4527/4613/4833` 四处都是
  `nullptr`），驱动退化为 `delay_for_interval(100, NSEC_PER_USEC)`
  （`NativeAdrenoPublish.cpp:674`）。XNU 的 `delay_for_interval` 在等待线程上是一次
  **定时器睡眠**，实际唤醒粒度是毫秒级，不是 100 µs。
- 同时 `timeouts=726`（23%）、`longest=874,685 µs`：超时后走 kick/stall 路径，帧就漏了。
- 根因之一还在于**中断不可达**：SPI 300 在 GIC group 0（`armcpu_spi_attach` 读回 `0x0000a002`，
  bit0=0），而内核只读 `icc_iar1_el1`；1502 次提交只收到 2 次中断。所以即使写了 `clock.idle`，
  也没有 IRQ 来唤醒它——必须先能"不靠中断也快"。

### D4 flip 前不等 GPU 写完 —— **硬**（正确性，不只是性能）

- 上游在 flip 前调 `gpuWrote()`：抓到 swap 时刻的 `submitted` 序号，等 `retired` 追上才翻页，
  200 µs 重试，≥8 ms 记 `direct[13]`（`upstream_NativeLegacyDisplay.cpp:375-413`），
  CPU 拷贝兜底也在 `:682` 用同一道门。
- **我们的 fork 里没有这个函数**（grep `native_adreno_fences|gpuWrote` 在
  `NativeLegacyDisplay.cpp` 零命中），`[direct scanout]` 也只有 9 个计数器，
  缺 `[9] 被 GPU 挡住的 swap 数 / [10] 累计等待 / [11] 最长 / [12] ≥250ms / [13] ≥8ms 漏帧`。
- 后果：面板可能扫到 GPU 还在写的 surface（撕裂/闪），而且我们**连"漏了几帧"都看不见**。
  asteroids T49 记过同一现象：663/703 次 flip 有未完成工作。

### D5 没有帧时间仪表 —— **仪表**

- 我们的 `[direct scanout]` 只有 flips/latch 统计；`[swap timeline]` 这一行**打出来是空的**
  （`BootLog.c:536` 有行，驱动侧没有对应的 ring）。
- `[dpu]`（每秒帧计数 + 行数 + vsync 周期）的组装代码在 `BootLog.c:1084-1089`，
  但生产者 `DisplayTimingProbe.cpp` **不在本仓库**，只有全零弱桩
  （`BootProgressStubs.c:230-231`），所以这一行**从未打印过**。
- 结果：我们没有任何一行能回答"面板此刻多少 Hz""这一帧是不是晚了"。

### D6 vsync 从未启用，且它本身是定时器 —— **软 + 风险**

- `sheng-vsync` 不在 `board.toml`（`[cmdline]` 实测 `len=992`，没有该参数）；
  于是 `startVsync()` 在 `hz==0` 处直接返回（`NativeLegacyDisplay.cpp:305-307`），
  六个计数器全 0（`vsync hz=0 sent=0 arms=0 idle=0 late=0 start=0 refresh=0`）。
- 不给合成器发布 1/120 刷新，RenderBox 就按 1/60 自节拍（原始 slot 301 把最小刷新固定成 1/60 s）。
- 机制是 `IOTimerEventSource`，不是面板 vblank（`NativeLegacyDisplay.cpp:74-78`）；sheng 也是定时器，
  所以这不是我们的短板，但**它意味着"节拍准度"要靠我们自己的 late 计数去证明**。
- 已知风险：`porting.toml:405` 记录过一次数据异常中止，`pc/lr` 落在 `startVsync()` 的 lambda 里
  （`x0=0x9c000000`、`esr=0x96000010`），归因被 `docs/gpu-direct-scanout-plan.md:163-169`
  明确留着没定论。**启用 vsync 前必须先解释或加护栏。**

### D7 死观测量与类型缺陷 —— **仪表**

- `native_gpu_perf_vote`、`native_gpu_idle_sleeps`、`native_gpu_idle_spins` 全树无写者，
  只有弱桩（`BootProgressStubs.c:127-128`、`:234`），而 `BootLog.c:700`、`:893` 在读
  → `[clocks] gpu perf 0 bw 0` 是"没接线"，不是"没性能"。
- 桩是 `uint64_t`、驱动与读取端是 `uint32_t`：驱动一旦没链进来，读到的是半个对象。
- `native_adreno_cp_aperture[0..3]`、`native_adreno_table_switches[0..7]`、
  `native_adreno_submit_phase[0..6]` **都不打印** —— 而它们正好能回答 D2/D3 的问题。

### D8 无 GPU DVFS、无 shader 预热 —— **软**

- `perf_index` 在开机时钉死 7 = 670 MHz（`DbyGpuPowerProbe.cpp:5904-5910`），
  `A650GmuSetFreq` 之后没人调用 → 全程满频（对 fps 有利，对功耗/发热不利）。
- DDR 带宽票只投一次（`DbyGpuPowerProbe.cpp:1076` 置 `A650GmuDdrVote=1`）。
- sheng 有 `gpu-dcvs=1`；j716f 有 `pipa-gpu-dcvs=1`（305–670MHz）。
- **shader 预热完全没有**：sheng 有 `--prime-list` / `--pipeline-pack`，
  首次编译会卡帧；diting 的记录直接把"UI 帧率受 pipeline 编译与 shader cache 限制"写进 limits。

### D9 直扫一次只允许一个 flip 在飞 —— **软（当前不是瓶颈）**

- `if(directOn && !gpuBypass && !latchRequest)`（`NativeLegacyDisplay.cpp:530`）串行化，
  每帧成本 = 一次完整 latch。当前 latch 均值 8.51 ms 是**因为面板 60Hz**；
  面板到 120Hz 后理论均值 ≈4.25 ms，也就是 ~235 fps 的均值上限，**不构成 120 的障碍**。
- 500 µs 轮询是 8.33 ms 的 6%，是量化误差，不是墙。

### D10 记录本身的口径错误 —— **文档**

- `porting.toml:521` 用 CPU 拷贝速率否 120（见 §0 第 2 条）；
- `porting.toml:522` 仍写 `sheng-dpu-scanout` "is absent from [payload] kernel_args"，
  而 `board.toml:796` 就是 `sheng-dpu-scanout=2`，同一份日志还是 `flips=118 / fallback=0` 的引导；
- `porting.toml:528` 的 `limits` 还写着 "No GPU code is implemented for this SoC."

**这十条里，D1 是唯一"不做就没有 120"的；D2/D3 是"不做就只有 24 帧"的；D4/D5 是"不做就不知道自己在哪"的。**

## 3. 物理与工程核算：A650 到底能不能扛 1600×2560@120

| 项 | 数字 | 判定 |
| --- | --- | --- |
| 一帧 | 1600×2560×4 B = 16,384,000 B | — |
| 扫描读出（120Hz） | 1.97 GB/s | — |
| GPU 写一帧 | +1.97 GB/s | — |
| 合成 3 层全屏（读 3 写 1） | ≈ 7.9 GB/s | — |
| kona LPDDR5 理论 | ≈ 44 GB/s | 占用 18%，**不是墙** |
| A650 填充率（8-bit BGRA，单层） | 1920 Mpx/s | — |
| overdraw 3.6 时 | ≈ 6.9 Gpx/s | 逼近但未越界；**必须走 GMEM 平铺**，否则 DRAM 往返翻倍 |
| CPU 拷贝兜底 | 153 MiB/s ⇒ 9.4–10.2 fps/整帧 | **完全不可用**，只能靠直扫 |

**结论**：120 的瓶颈不在 SoC 的算力或带宽，而在
（a）面板没切档，（b）每帧的软件延迟（42 ms 级），（c）没有帧级观测。

## 4. 实施方案

原则（与仓库规则一致）：**一次只改一个变量；先仪表后优化；每步都要有"上机看哪一行"；
每步都要有回退路径。** 顺序按"依赖"而不是按"看起来重要"排。

### P0 —— 先造仪表（1 次 flash，不改行为）

**为什么先做**：D1 的判定只能靠 latch 间接推、D2/D3 只能靠总数平均；没有帧级数据，
后面每一步都是盲调。sheng/asteroids 都证明了"先有 `[frame time]` 才谈得上调"。

**改什么**（全部是"只加打印/只加计数"，不动控制流）：

1. `[frame]`：在 `latchTick()` 与 `flip()` 里记录相邻 flip 的间隔，按
   `≤8.33 / 8.33–16.7 / 16.7–25 / 25–34 / >34 ms` 分桶，并输出 p50/p95/max —— 照 asteroids 的
   `[frames]` 口径，另外单独给一个"120Hz 预算内比例"。
2. `[gpu submit] p0..p6`：把驱动已经在累加的 `native_adreno_submit_phase[0..6]`
   （`NativeAdrenoSubmit.cpp:19`、`:568`）打出来，直接回答"42 ms 花在哪一段"。
3. `[gpu ttbr]`：打印 `native_adreno_table_switches[0..7]` 与 `native_adreno_cp_aperture[0..3]`
   → 确认表切模式是不是恒为 1、每次提交是否真的排空。
4. `[panel]`：把 `[dpu]` 那一行补上生产者 —— 读 DPU/DSI 的帧计数两次（间隔 1 s），
   给出**实测刷新率**；同时把 DSI 的 `vtotal`/`VFP` 寄存器值打出来（哪怕只是读）。
   （`BootLog.c:1084-1089` 的组装已经在，缺的是 `DisplayTimingProbe.cpp` 的采集端。）
5. 顺手把 D7 的两个类型统一、把三个死观测量接上真值（或从行里删掉）。

**上机看哪一行 / 通过标准**：
`[panel] fps=59.9`（预期 60 左右）、`[frame]` 有分布、`[gpu submit]` 各段有值、
`[gpu ttbr] mode=1 switches>0`。**任何一行没出来，说明改动没生效，不要往下走。**

**风险**：几乎为零（只加计数器）；唯一风险是打印量，按"每 1 秒一行"限流。

### P1 —— 让等待变廉价（1 次 flash）

**为什么**：D3 的 1.60 ms/poll 是 42 ms 的乘数；先把乘数从 16× 降到 1×。

**改什么**：给驱动提供板级 `clock.idle`，**第一版只做最简单、最不可能阻塞的形式**：

```
若已 attach 到 GPU 中断：assert_wait_timeout(IRQ 事件, 100 µs)   // 有 IRQ 时最省
否则：IODelay(20) 自旋若干次，然后退回 100 µs 睡眠               // 无 IRQ 时的快路径
两种都计入 native_gpu_idle_sleeps / idle_spins（把死观测量接活）
返回值语义：非零 = "该结束这次等待了"，不是"睡了多久"
```

**为什么先只做这个**：上次写 idle 回调把 UI 弄死（payload `164b4a52`，`flips=1846` 后停住），
原因是那版在回调里做了**不可调度的阻塞**。`IODelay(20)` 是纯忙等，不睡眠、不持锁、
不依赖线程状态，是风险最低的起点；`assert_wait_timeout` 只在 IRQ 已 attach 时才走。

**评审要求（上机前必须做）**：把回调在主机侧的状态机测试里跑一遍（`drivers/Adreno740/tests/`
有 hostsim 框架），证明它在"fence 立即到 / 永不达 / 中途超时"三种情况下都只返回、不阻塞。

**上机看哪一行 / 通过标准**：
`[fence wait] ... polls=...` 的 poll 数不涨而 `us` 大降；`polls/waits` 约 1–2；
`[coherence]` 的 slept/spun 从 0 变成非零；`timeouts` **不升**；`[gpu methods] 5` 均值明显下降
（预期 42 ms → 数 ms 级）。

**风险**：中。回退 = 保持 `clock.idle = nullptr`（一行）。

### P2 —— 去掉"换页表前排空 ring"（1 次 flash）

**为什么**：D2。即使 poll 变快，mode 1 仍然让每次跨 VM 提交等全 ring 静默；
7 个客户端交替提交时这等于"每次提交等一帧"。

**改什么**（两条路，优先第一条）：

1. **打开 CP 的 SMMU aperture，然后强制 mode 2**：
   板级实现 `qcom_scm_set_gpu_smmu_aperture`（我们已有 SMC 基础设施：
   `DbyGpuPowerProbe.cpp:3196-3261` 已经在用 SIP SMC 做 PAS），把它返回写进
   `native_adreno_cp_aperture[0]/[1]`；然后 `sheng-gpu-ttbr=2`（我们 fork 的
   `tableMode()` 会认这个参数，`NativeAdrenoPublish.cpp:179`）。
2. 若 SCM 调用不可用/被拒：**退而减少换表次数** —— 让同一客户端的连续提交留在同一张表里
   （驱动已有 `vm==table_vm_` 的短路），并把 `waitAll` 的上限从 2 s 降到"一个帧预算"
   （例如 20 ms），使异常路径不再拖死帧。

**上机看哪一行 / 通过标准**：`[gpu submit] phase5` 从数十 ms 降到 < 1 ms；
`[gpu methods] 5` 均值 < 2 ms；`[gpu ttbr] mode=2`；`native_adreno_cp_image` 的表切换检查通过
（`Publish.cpp:1150-1178` 已有这条检查）。

**风险**：中高（CP 换表错会 fault）。回退 = `sheng-gpu-ttbr=1`（一个参数）。
**前置**：P0 的 `[gpu submit]` 必须已证明"phase5 是最大头"，否则不做这步。

### P3 —— 补上"flip 前等 GPU 写完"，并让漏帧可见（1 次 flash）

**为什么**：D4/D5。这是正确性 + 可观测，双份收益；也是 120 验收里
"missed-vblank < 0.5%" 唯一能算出来的前提。

**改什么**：移植上游三件（都是 Null 默认的板级钩子，缺失即保持现状）：

- `gpuWrote()`：flip 前抓 `submitted` 序号，等 `retired`；200 µs 重试；
  超时走原有兜底（`upstream_NativeLegacyDisplay.cpp:375-413`）；
- `native_legacy_direct[9..13]`：被挡住的 swap、累计等待、最长等待、≥250 ms、**≥8 ms（漏帧）**；
- `native_legacy_ring` / `native_legacy_swapstat[16]`：swap 生命周期环（验证/等待/flip/latch/退休），
  让 `[swap timeline]` 不再是空行。

**上机看哪一行 / 通过标准**：`[direct scanout]` 出现 `held=N wait=..ms max=.. missed=..`；
`missed / held < 0.5%`；画面无撕裂；`[swap timeline]` 有事件。

**风险**：低–中（门会让每帧多等一次 GPU；如果 GPU 慢于面板，帧率会掉——但那正是要测的）。
回退 = 不调 `gpuWrote()`（保持现状）。

### P4 —— 面板切 120Hz（独立的显示工程，1 次 boot flash）

**为什么**：D1，唯一的硬门。

**做什么**：把 DSI 时序的 `vtotal` 从 5654 改成 **2827**（`vbp/vsync/vfp = 4/4/26`），
pixel clock **不变**（584849 kHz），配合一次 full modeset + 面板 off/on
（104 条开屏命令 + 5 条关屏命令，来自设备原厂的运行时 FDT，不在仓库里 —— 这是本步的输入）。

**放在固件侧做，不在 XNU 侧做**，理由是：面板初始化表已经在固件里（固件的显示驱动本来就要把面板点亮），
XNU 侧只读 GOP 模式；在固件里改一行 `vtotal` 就等于"整机从第一帧起就是 120Hz"，
既不用把 104 条命令搬进内核，也不会碰到记录里那个"DSI kick 打断触摸"的坑。

**上机看哪一行 / 通过标准**：`[panel] fps=120.0`；`[direct scanout] longest` 从 ~16.8 ms
降到 ~8.4 ms；`[frame]` 分桶中心移到 8.33 ms；桌面不闪不裂、触摸正常。

**风险**：高（改固件显示初始化，可能点不亮 / 花屏 / 触摸失效）。
回退 = 保留当前 60Hz boot image；**一次只改 vtotal，先不动 lane/PLL**。
**前置**：P0 的 `[panel]` 必须先能测出 60.0，否则改了也不知道成没成。

### P5 —— 把 1/120 告诉合成器（1 次 payload 重建，最便宜的一步）

**为什么**：D6。面板到 120 之后，如果 RenderBox 还按 1/60 节拍，就永远不会请求 120 帧。

**改什么**：`board.toml [payload] kernel_args` 加 `sheng-vsync=120`。
我们的 fork 已经支持：`registerService()` 在 `hz>60` 时发布 `IOMFBDisplayRefresh`
（`NativeLegacyDisplay.cpp:409-410`），`getRefreshAttributes()` 在 `fixed || locked` 时把
最大间隔也压成 1/120（`:419-430`）。`sheng-vsync-fixed=1` **可以不加**（`fixed` 入参已覆盖）。

**字节预算**：当前 committed 版 55 参数 / **983 字节**，上限 1000 → 余 17；
`sheng-vsync=120` + 一个空格 = **16 字节**，**刚好放得下（999/1000）**。
注意另一个会话的无线工作要往同一份参数表里加东西，会撞预算 —— 加之前先确认。

**上机看哪一行 / 通过标准**：`[swapok] ... vsync hz=120 arms>0 sent>0 late≈0`；
`[frame]` 的 p50 落在 8.33 ms 附近；`[mfb clients]` 里出现 vsync 客户端。

**风险**：中（`porting.toml:405` 那次 abort 就落在 vsync 路径）。
**前置**：先解释或护栏那次 abort；这一轮**单独做、单独回退**；
另外注意上游已把参数名从 `sheng-vsync` 改成 `vsync`，我们 fork 仍认旧名——
不要在同一轮里改名，否则"改了没生效"会变成假阴性。

### P6 —— 软件侧收尾（1 次 payload / addon 重建）

- **shader 预热**：照 sheng 的 `--prime-list`（每个 `.metallib` 的绝对路径）+
  `make-gpu-addon.py --pipeline-pack`（把上一轮跑出来的缓存打包进 addon）。
  目标是"桌面第一次出现时不编译"。
- 确认 Turnip 走 `TU_DEBUG=gmem,nocb`（GMEM 平铺），并把 `metal-flow` 保持 0
  （sheng 实测 metal-flow=1 反而更慢：67.4/73.2 vs 72.1/68.2）。
- 减少 CA 过绘制：壁纸冻结、少用模糊层（asteroids 的教训：3.6 层全屏是它上不去 120 的主因）。

**上机看哪一行 / 通过标准**：首帧后 10 s 内无 > 33 ms 帧；`[metal]` 行不再出现按需编译；
`[gpu jobs]`（若移植）无 > 8 ms 的 job。

### P7 —— 验收与门

- 连续 60 s 前台动画：**p50 ≤ 8.4 ms、p95 ≤ 8.4 ms、missed-vblank < 0.5%、无 > 33 ms 长帧、
  无 CP 重启**。
- 把 sheng 的 `analyze-sheng-frame-timing.py` 式的判定搬过来，**默认 `qualifies_stable_120fps=False`**，
  只有数据满足才置真 —— 避免"自己给自己发证书"。
- 达不到时回退目标 = 稳定 60（p95 ≤ 16.8 ms），并把瓶颈写进 `porting.toml` 的 gpu/display 记录。

## 5. 顺序、依赖与预算

| 步骤 | 依赖 | 需要什么 | 预期收益 | 风险 |
| --- | --- | --- | --- | --- |
| P0 仪表 | 无 | kernel flash | 让后面每一步可判 | 极低 |
| P1 `clock.idle` | P0（要先看到 phase 分布） | kernel flash | submit 42 ms → 数 ms | 中 |
| P2 CP 换表 mode 2 | P1 的 phase 结论 | kernel flash + SCM | 去掉每帧排空 | 中高 |
| P3 fence 门 + 漏帧计数 | 无 | kernel flash | 正确性 + missed 可见 | 低–中 |
| P4 面板 120Hz | P0 的 `[panel]` | **boot flash（固件）** | 打开 8.33 ms 预算 | 高 |
| P5 `sheng-vsync=120` | P4 | payload 重建 | 合成器按 120 节拍 | 中 |
| P6 shader 预热 | P5 | payload/addon 重建 | 去掉首帧编译尖峰 | 低 |
| P7 验收 | 全部 | 一次 60 s 跑 | 判定达标/回退 | — |

**关键路径**：P0 → P1 → P2（延迟）∥ P3（观测）→ P4（面板）→ P5 → P6 → P7。

**预计 flash 次数**：7 次左右（kernel 4 次、boot 1 次、payload 2 次）。
按"一次一个变量"的规则，不建议压缩。

## 6. 不做的事（以及为什么）

| 不做 | 理由 |
| --- | --- |
| 移植 `NativeAdrenoPreempt` | A6xx **没有硬件抢占**（`NativeAdrenoIrq.h:52` 自己写着 "A6xx has no preemption (no CP_SW)"），gts7xlwifi 里运行期也没有调用者 |
| 移植 `NativeGpuPerfCounters` | A7XX 专用的 19 计数器 BR 方案，A650 没有这个块 |
| 追 "120 是 A840 的数" 这种类比 | pandora 的 110 帧没有工具支撑；sheng 的 72 也没有；拿别人的口径当自己的上限，会把"没测过"当成"做不到" |
| 继续优化 CPU 拷贝路径 | 153 MiB/s ⇒ 9.4–10.2 fps，天生不可用；直扫已经 `fallback=0` |
| 把 10-bit / HDR 拉回来 | 8-bit BGRA 是直扫的前提，当前 surface 已是 `0x42475241`（stride 6400），退回 10-bit 会重新触发 `REJ fmt=62336138` |
| 在 P4 之前调 GPU 频率/DCVS | 面板 60Hz 时，GPU 再快也只出 60 帧；先开预算再谈功耗 |

## 7. 未决问题（需要 owner 或外部输入）

1. **面板开屏命令表（104+5 条）从哪来？** 本仓库没有（`DBY-W09-display-research.md:99-100`
   说它从设备原厂运行时 FDT 提取）。P4 依赖它；如果固件里已有，就不用重取。
2. **`qcom_scm_set_gpu_smmu_aperture` 的 call id / ABI**：本仓库与两个兄弟板都**没有**实现
   （gts7xlwifi/alioth 的 probe 里零命中），需要从核心 `Adreno740` 或 sheng 的 package 里确认。
   这决定 P2 走"mode 2"还是走"降低 waitAll 上限"。
3. **`porting.toml:405` 那次 vsync 路径 abort 是否已修？** 未定论，P5 的前置。
4. **120Hz 下 DSI/DPU 的 lane rate 与 PHY 是否仍满足？** 同 PLL、只改 VFP 意味着
   link rate 不变、行长不变，理论上安全，但需要 P4 的第一次点亮来证。
5. **热设计**：120Hz + GPU 满频的持续功耗/温升没有数据；P7 的 60 s 跑要同时记录
   电池电流与 SoC 温度。
